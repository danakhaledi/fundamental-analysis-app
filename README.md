# سامانه تحلیل بنیادی بورس — نسخه ۳۴.۶

## نسخه v34.7 — مرجع یکتای نمادها از TSETMC
- تنها منبع ورود هویت ابزارهای معاملاتی به `MarketSymbols`، APIهای رسمی TSETMC است؛ مسیر دریافت MarketWatchPlus Excel و فایل‌های محلی از این فرآیند حذف شده است.
- هر رکورد باید `InsCode` رسمی و عددی داشته باشد. ثبت و به‌روزرسانی بر اساس `InsCode` انجام می‌شود، نه نام نماد؛ بنابراین ابزارهای مستقل با نماد یکسان با هم ادغام نمی‌شوند.
- دریافت از API جدید و قدیمی TSETMC انجام می‌شود و پیش از ثبت، اندازه snapshot با حداقل پوشش مورد انتظار و تعداد قبلی کنترل می‌شود. پاسخ ناقص یا کم‌حجم پذیرفته نمی‌شود.
- گزارش‌های Excel کدال فقط مصرف‌کننده مرجع نمادها هستند. برای ثبت گزارش، نماد باید از طریق رکورد فعال و دارای `InsCode` رسمی در `dbo.MarketSymbols` به یک `CompanyID` معتبر متصل باشد؛ اطلاعات کدال برای ساخت نماد، شرکت یا صنعت جایگزین استفاده نمی‌شود.
- رکوردهای ساختگی قدیمی به‌صورت نرم غیرفعال می‌شوند؛ رکوردها و تاریخچه وابسته حذف نمی‌شوند. ستون قدیمی `InstrumentCodeIsPlaceholder` صرفاً برای سازگاری دیتابیس‌های موجود حفظ شده و در مسیر ایجاد نماد جدید کاربرد ندارد.
- عملیات دستی دو مرحله مستقل دارد: «تازه‌سازی فهرست نمادها» فقط SQLite را تغییر می‌دهد و «انتقال نمادهای رسمی» با اقدام جداگانه مدیر به SQL Server منتقل می‌کند. جاب روزانه زمان‌بندی‌شده همچنان گردش‌کار کامل تازه‌سازی، انتقال و تاریخچه را اجرا می‌کند؛ فرآیند resolve شناسه‌های موقت حذف شده است.

## تغییرات مرکز دریافت کدال در v34.6
- عملیات تولید/فروش و خرید/مصرف از ثبت‌کننده مشترک شرکت و سند استفاده می‌کنند.
- تطبیق نماد گزارش فقط از طریق `dbo.MarketSymbols` و اتصال رسمی آن به `dbo.Companies` انجام می‌شود. اگر اتصال یکتای معتبر وجود نداشته باشد، پردازش گزارش متوقف و خطای تطبیق گزارش می‌شود.
- نام شرکت و صنعت از متن گزارش کدال حدس زده یا به‌عنوان جایگزین رجیستری رسمی ایجاد نمی‌شوند؛ مرجع شرکت و صنعت، شناسه‌های TSETMC است.

- این تغییر به اسکریپت مهاجرت یا تغییر ساختار SQL نیاز ندارد.

## راهنمای پایه (نسخه ۳۱ و تغییرات تاریخی)

## ورود اولیه
- نام کاربری: `admin`
- کلمه عبور: `admin`

در اولین ورود، تغییر رمز اجباری است. رمزها با PBKDF2 هش می‌شوند. مدیر می‌تواند از صفحه «تنظیمات سامانه و کاربران» حساب کاربر بسازد، سیاست اجبار تغییر رمز در اولین ورود را برای هر حساب تنظیم کند، تغییر رمز در ورود بعدی را اجباری کند و حساب‌ها را فعال/غیرفعال کند. ایجاد کاربر و تنظیمات کاربران فقط برای نقش ADMIN مجاز است.

## اجرا در ویندوز
1. Python 3.11+ نصب باشد.
2. `run_windows.bat` را اجرا کنید. اسکریپت ابتدا نصب وابستگی‌ها را از PyPI رسمی امتحان می‌کند؛ اگر نصب ناموفق باشد، به‌طور خودکار یک بار از میرور Aliyun استفاده می‌کند. اگر هر دو روش شکست بخورند، برنامه اجرا نمی‌شود و خطا برای بررسی نمایش داده می‌شود.
3. فایل `.env` را باز کنید؛ `APP_SECRET_KEY` را به یک کلید تصادفی طولانی تغییر دهید.
4. برای داده زنده، `SQLSERVER_CONNECTION_STRING` را مطابق سرور خود تنظیم کنید. گزینه `LongAsMax=Yes` برای سازگاری رشته‌های بلند با Collationهای UTF-8/SC به‌صورت خودکار به اتصال افزوده می‌شود.
5. در مرورگر به `http://127.0.0.1:8000` بروید.

برای SQL Server، درایور ODBC سازگار باید نصب باشد. برنامه بدون اتصال نیز اجرا می‌شود؛ در آن حالت صفحات داده خطای اتصال را نشان می‌دهند.

## تنظیمات کاربران
- ساخت کاربر از صفحه «تنظیمات سامانه و کاربران»؛ نام کاربری ۳ تا ۵۰ نویسه و فقط حروف انگلیسی، عدد، `-` و `_` است. رمز اولیه باید حداقل ۱۰ نویسه داشته باشد.
- گزینه «اجبار تغییر رمز در اولین ورود» برای هر حساب جداگانه ذخیره می‌شود.
- مدیر می‌تواند تغییر رمز در ورود بعدی را اجباری و حساب‌های دیگر را فعال/غیرفعال کند. حساب مدیر نمی‌تواند خودش را غیرفعال کند.
- مهاجرت پایگاه احراز هویت SQLite به‌صورت افزایشی در شروع برنامه انجام می‌شود؛ دیتابیس SQL Server و داده‌های تحلیل بنیادی تغییر نمی‌کنند.

## صفحات اولیه
داشبورد، فروش ماهانه (`dbo.vw_MonthlySales`)، پیش‌بینی (`dbo.vw_ForecastEffectiveValues` و `dbo.vw_ForecastCalculatedValues`)، ارزش‌گذاری (`dbo.vw_CurrentTTM` و `dbo.vw_CurrentPE`) و وضعیت اتصال.

## امنیت
برای استقرار شبکه‌ای HTTPS و کلید محرمانه قوی تنظیم کنید. رشته اتصال حاوی رمز را در فایل `.env` نگه دارید و فایل را به اشتراک نگذارید. حساب SQL را فقط با حداقل دسترسی لازم ایجاد کنید.


## Windows startup and password change

Run `run_windows.bat`. It detects Python 3.11+ using `py` or `python`, creates `.venv` if needed, tries the official PyPI index first, and falls back to the Aliyun mirror if installation fails. The batch file uses ASCII-only command text to avoid Windows code-page issues.

On first login, users whose account policy requires a password change are sent to the password form. The form asks for the current password, a new password of at least 10 characters, and confirmation.


## تنظیم اتصال SQL Server از داخل برنامه

در حساب مدیر به صفحه تنظیمات بروید. بخش «تنظیمات اتصال به SQL Server» امکان آزمون و ذخیره اتصال با SQL Server Authentication (از جمله sa) یا Windows Authentication را فراهم می‌کند. تنظیم ذخیره‌شده در `app_auth.db` رمزگذاری می‌شود؛ کلید رمزگذاری از `APP_SECRET_KEY` مشتق می‌شود. پس از ذخیره تنظیمات، `APP_SECRET_KEY` را تغییر ندهید؛ تغییر آن باعث می‌شود تنظیم ذخیره‌شده قابل رمزگشایی نباشد. قبل از تغییر کلید، از `app_auth.db` نسخه پشتیبان بگیرید. رمز اتصال در فایل‌های گزارش یا صفحه تنظیمات نمایش داده نمی‌شود.

درایور ODBC انتخاب‌شده باید از قبل روی ویندوز نصب باشد. استفاده از `sa` توصیه نمی‌شود مگر در محیط آزمایشی؛ برای استفاده دائمی حساب SQL با حداقل مجوزهای لازم بسازید.


## مرکز دریافت کدال (نسخه اولیه)

پس از ورود مدیر به برنامه، از منوی «مرکز دریافت کدال» می‌توان گزارش‌های فعالیت ماهانه و صورت‌های مالی را بر اساس نماد جست‌وجو کرد و پیوست‌های Excel موجود را دانلود نمود. در صورت خالی گذاشتن نماد، جست‌وجو به‌صورت عمومی انجام می‌شود؛ برای کنترل حجم پاسخ، تعداد صفحات محدود است.

فایل‌ها در مسیر `data/codal_downloads` زیر پوشه اصلی برنامه ذخیره می‌شوند و `manifest.json` اطلاعات دانلودها را نگه می‌دارد. دانلود فایل موجود دوباره انجام نمی‌شود. این بخش در حال حاضر فقط دریافت و ثبت فهرست فایل‌ها را انجام می‌دهد و به‌صورت عمدی اطلاعاتی را به جداول مالی SQL Server وارد نمی‌کند.

**وضعیت پردازش منابع در v31:** عملیات «استخراج و ثبت خرید/مصرف در Stage» از `Table_2` و `Table_3` گزارش فعالیت ماهانه، فقط مقادیر دوره یک‌ماهه و ستون‌های اصلاحات را استخراج می‌کند، نام منابع را با `dbo.ProductMappings` تطبیق می‌دهد و خروجی را در `dbo.CompanyResourceTransactions_Stage` ثبت می‌کند. ردیف‌های فاقد نگاشت، واحد استاندارد یا دارای اختلاف واحد با مرجع محصول با وضعیت `INVALID` و پیام کنترل ثبت می‌شوند. مقادیر خالی `NULL` می‌مانند، صفر صریح منبع صفر ثبت می‌شود، مبلغ با مقیاس گزارش (میلیون ریال) نگهداری می‌شود و تبدیل واحد انجام نمی‌شود. اجرای مجدد برای یک `SourceDocumentID` ابتدا ردیف‌های همان سند را در Stage جایگزین می‌کند تا تکرار ایجاد نشود. در صورت نبود SourceDocument عادی، فقط فراداده سند ایجاد می‌شود؛ گزارش اصلاحی بدون رابطه اصلاحیه صریح ثبت نمی‌شود. این عملیات به جدول نهایی `dbo.CompanyResourceTransactions` داده‌ای درج یا حذف نمی‌کند.

ثبت فروش در `dbo.ProductionSales_Stage` و انتقال کنترل‌شده منابع از Stage به جدول نهایی، مراحل مستقل بعدی هستند و در این نسخه فعال نشده‌اند.

## مرکز دریافت کدال - انتخاب نماد و فایل

- نمادهای منتخب در جدول `codal_watchlist` داخل پایگاه داده محلی برنامه (`app_auth.db`) نگهداری می‌شوند؛ این جدول مستقل از جداول مالی SQL Server است.
- در صفحه «مرکز دریافت کدال» می‌توان یک یا چند نماد منتخب را برای جست‌وجو علامت زد.
- در نتایج جست‌وجو، فایل‌های دارای پیوست Excel قابل انتخاب هستند. اگر هنگام دانلود هیچ گزارشی انتخاب نشده باشد، همه نتایج جست‌وجو دانلود می‌شوند.
- برای کاهش احتمال timeout، جست‌وجوی عمومی بدون نماد فقط یک صفحه محدود را بررسی می‌کند و درخواست‌های Codal دارای timeout محدود هستند. برای جست‌وجوی گسترده، نمادهای منتخب را به‌صورت گروهی انتخاب کنید.
- دانلود فایل به‌تنهایی اطلاعاتی را در جداول مالی SQL Server وارد نمی‌کند.

## مدیریت نمادها و فهرست مرجع بازار

جدول محلی `market_symbols` مرجع هویت ابزارهای معاملاتی است و فقط از APIهای TSETMC تغذیه می‌شود. API جدید `ClosingPrice/GetMarketWatch` و API قدیمی `MarketWatchInit` منابع دریافت هستند؛ اگر پاسخ‌ها ناقص یا کمتر از حد پوشش مورد انتظار باشند، همگام‌سازی متوقف می‌شود و داده‌های قبلی دست‌نخورده می‌مانند. هیچ فایل Excel، پوشه Downloads یا گزارش کدال در مسیر ورود نمادها استفاده نمی‌شود.

کلید هویت هر ابزار `InsCode` رسمی TSETMC است. نام نماد یکتا فرض نمی‌شود و چند ابزار با نماد یکسان به‌صورت رکوردهای مستقل نگهداری می‌شوند. شناسه‌های `insCode2/3/4` بدون اعتبارسنجی مستقل به‌عنوان ابزار جداگانه تلقی نمی‌شوند.

در عملیات دستی صفحه مدیریت نمادها، ابتدا «دریافت / تازه‌سازی از TSETMC» اجرا می‌شود که فقط SQLite محلی را به‌روزرسانی می‌کند؛ سپس مدیر باید «انتقال نمادهای رسمی به SQL Server» را جداگانه اجرا کند. همگام‌سازی رجیستری شرکت‌ها و صنایع و دریافت تاریخچه دستی، انتقال خودکار انجام نمی‌دهند و در صورت ناقص بودن انتقال، با پیام روشن متوقف می‌شوند. جاب روزانه زمان‌بندی‌شده یک گردش‌کار مستقل است و انتقال را به‌عنوان مرحله مشخص خود اجرا می‌کند.

گزارش‌های کدال (از جمله فایل‌های Excel فعالیت ماهانه و صورت‌های مالی) فقط نماد گزارش را در `MarketSymbols` جست‌وجو می‌کنند و از اتصال رسمی آن به `Companies` برای ثبت داده در جداول تخصصی استفاده می‌کنند. اگر نماد فعال با InsCode رسمی و CompanyID یکتا پیدا نشود، گزارش برای بررسی متوقف می‌شود؛ از نام شرکت یا متن Excel نماد/شرکت ساختگی ایجاد نمی‌شود.

در شروع برنامه، رکوردهای قدیمی دارای شناسه موقت یا غیرعددی به‌صورت نرم غیرفعال می‌شوند. در SQL Server نیز placeholderهای قدیمی غیرفعال می‌شوند؛ هیچ رکورد یا تاریخچه وابسته‌ای در این مرحله حذف نمی‌شود. ستون legacy `InstrumentCodeIsPlaceholder` فقط برای سازگاری با دیتابیس‌های قبلی باقی مانده است.

## انتقال اطلاعات بازار به SQL Server (نسخه 13)

پس از اجرای اسکریپت `01_CreateMarketTables.sql` و ایجاد جدول‌های `dbo.MarketSymbols` و `dbo.MarketDailyData`، با حساب مدیر وارد صفحه «مدیریت نمادها» شوید و «بررسی و انتقال اطلاعات بازار به SQL Server» را انتخاب کنید. ابتدا شمارش رکوردها نمایش داده می‌شود؛ انتقال فقط پس از فشردن دکمه تأیید انجام می‌شود.

انتقال، رکوردهای محلی SQLite را حذف نمی‌کند و در مقصد نیز فقط رکوردهای جدید را درج می‌کند. برای نمادها از `LocalSymbolID` و `InsCode` و برای داده‌های روزانه از `LocalMarketDataID` برای جلوگیری از انتقال تکراری استفاده می‌شود. مقادیر بازار به شکل متن اصلی نگهداری می‌شوند تا تبدیل عددی یا گرد کردن ناخواسته رخ ندهد. این قابلیت فقط دو جدول بازار را هدف می‌گیرد و به `dbo.ProductionSales_Stage`، `dbo.ProductionSales` یا سایر جداول مالی دست نمی‌زند.

## تاریخچه روزانه قیمت‌ها (نسخه ۱۵)
برای جدول موجود `dbo.MarketDailyData`، ابتدا اسکریپت `02_AddTradeDateAndHistoryIndex.sql` را یک بار در دیتابیس اجرا کنید. این اسکریپت فقط ستون nullable `TradeDate` و ایندکس یکتای `(InsCode, TradeDate)` را برای ردیف‌های تاریخ‌دار اضافه می‌کند؛ ردیف‌های snapshot موجود دست‌نخورده می‌مانند. سپس از «مدیریت نمادها» > «مدیریت تاریخچه قیمت‌ها» دریافت اولیه را در دسته‌های ۱۵ نمادی ادامه دهید تا تکمیل شود. برای دفعات بعد از گزینه «به‌روزرسانی دسته بعدی» استفاده کنید و آن را تکرار کنید تا چرخه همه نمادها بگردد. منبع داده، API تاریخچه روزانه TSETMC است. کدهای جایگزین/ساختگی کنار گذاشته می‌شوند. دریافت تاریخچه در این نسخه باید از سیستم کاربر و اتصال واقعی به SQL Server آزمایش شود؛ دسترسی API می‌تواند بسته به شبکه یا محدودیت سرویس متفاوت باشد.

- صفحه جاب خلاصه مرحله‌ای را نشان می‌دهد و هر ۱۵ ثانیه تازه می‌شود.

- گزینه انتقال قدیمی از کارت‌های اصلی مدیریت نمادها حذف شد. این ابزار فقط برای مهاجرت داده‌های تاریخی که قبلاً در SQLite محلی بوده‌اند کاربرد دارد؛ جاب جاری نمادهای رسمی را به SQL Server منتقل می‌کند و تاریخچه را مستقیماً در SQL Server می‌نویسد.


## مرکز کدال نسخه ۳۰
انتخاب نماد در جست‌وجو اختیاری است. دکمه «استخراج اطلاعات در سیستم» ردیف‌های شیت‌ها را در بسته JSON آماده می‌کند. دکمه مستقل «استخراج و ثبت خرید/مصرف در Stage» داده‌های دوره جاری را از `Table_2` و `Table_3` استخراج و پس از تطبیق با `ProductMappings` در `CompanyResourceTransactions_Stage` قرار می‌دهد. این دکمه جدول نهایی منابع را تغییر نمی‌دهد. داده‌های خام JSON نیز برای بازبینی قابل دریافت هستند.

## مرکز دریافت کدال — نسخه v33
وضعیت مستقل جست‌وجو، دانلود، استخراج و ثبت منابع در همان پایگاه داده اصلی SQL Server و در جدول `dbo.CodalReportWorkflow` نگهداری می‌شود؛ فایل SQLite جداگانه برای گردش کار کدال ایجاد نمی‌شود. جدول `dbo.CodalWorkflowMeta` نشانگر مهاجرت سوابق قبلی را نگهداری می‌کند. پیش از اجرای نسخه، اسکریپت `00_CreateCodalWorkflow.sql` را یک‌بار روی پایگاه داده اصلی اجرا کنید. در اولین ورود، سوابق نسخه v32 و فایل‌های manifest/extraction قدیمی در صورت وجود به SQL Server منتقل می‌شوند. فایل SQLite قدیمی را تا تأیید مهاجرت حذف نکنید. برای جزئیات به `CHANGELOG_v33_FA.md` مراجعه کنید.


## نسخه v34.4 - اصلاح مهاجرت خودکار Stage محصولات

در نسخه v34.4، مهاجرت حداقلی `dbo.CodalProductStage` هنگام اجرای عملیات «دریافت محصولات/مواد» به‌صورت خودکار انجام می‌شود. ستون‌های `TracingNo`، `Symbol` و `ReportTitle` در صورت نبود اضافه می‌شوند؛ وابستگی‌های قدیمی به `Companies` و `SourceDocuments` حذف و ستون‌های شناسه سند/شرکت nullable می‌شوند؛ قید وضعیت برای `PENDING` اصلاح می‌شود. همچنین گزارش‌های موفق قدیمی v34.2 فقط یک‌بار برای بازپردازش به `PENDING` برمی‌گردند. برای این اصلاح نیازی به اجرای اسکریپت SQL جداگانه نیست. حساب اتصال SQL Server باید مجوز تغییر ساختار جدول و ایندکس را داشته باشد.

## نسخه v34.3 - مرکز دریافت کدال

### مهاجرت دیتابیس
پس از جایگزینی برنامه، فایل به‌روزشده `03_CodalWorkflow_v34.sql` را یک‌بار روی همان دیتابیس SQL Server برنامه اجرا کنید. اسکریپت علاوه بر تغییرات گردش کار v34، جدول `CodalProductStage` را به Stage عمومی تبدیل می‌کند: وابستگی اجباری آن به `Companies` و `SourceDocuments` حذف می‌شود و ستون‌های `Symbol`، `TracingNo` و `ReportTitle` اضافه می‌شوند. رکوردهای قبلی Stage حذف نمی‌شوند. وضعیت موفق عملیات محصولاتِ نسخه v34.2 نیز فقط یک‌بار به `PENDING` برمی‌گردد تا گزارش‌های قبلی در Stage عمومی جدید بازسازی شوند؛ ایجاد محصول و نگاشت تکراری به‌صورت idempotent کنترل می‌شود. اجرای مجدد اسکریپت امن است.

### گردش کار کدال
1. جست‌وجو: اگر نمادی انتخاب نشود، جست‌وجوی عمومی کدال همه نمادها را پوشش می‌دهد و صفحه‌های API تا پایان نتایج پیمایش می‌شوند.
2. صفحه‌بندی رابط کاربری: پیش‌فرض ۵۰ ردیف، قابل تنظیم به ۱۰۰، ۱۵۰ یا ۲۰۰ ردیف.
3. دانلود و استخراج: یک عملیات واحد؛ فایل‌های معتبر موجود دوباره دانلود نمی‌شوند و گزارش‌های استخراج‌شده دوباره استخراج نمی‌شوند.
4. سه عملیات مستقل پس از استخراج:
   - محصولات/مواد: نام‌های منبع از Table_1، Table_2 و Table_3 ابتدا در `CodalProductStage` ثبت و بلافاصله با `Products` و `ProductMappings` تطبیق داده می‌شوند. اگر معادل یکتا وجود داشته باشد، همان `ProductID` استفاده و نگاشت نام خام ثبت می‌شود. اگر معادل وجود نداشته باشد، محصول جدید با `ProductCode` سیستمی و پایدار از نوع `CODAL_<SHA256>` ایجاد و نگاشت آن ثبت می‌شود. موارد چندمعنایی یا ناسازگاری واحد برای بررسی باقی می‌مانند. این عملیات به `Companies` و `SourceDocuments` وابسته نیست.
   - تولید/فروش: اطلاعات ماه جاری Table_1 با کنترل سرستون‌ها در ProductionSales_Stage ثبت و پس از معتبر بودن تمام ردیف‌های گزارش به ProductionSales منتقل می‌شود.
   - خرید/مصرف: Table_2 و Table_3 در CompanyResourceTransactions_Stage اعتبارسنجی می‌شوند و پس از معتبر بودن تمام ردیف‌ها به CompanyResourceTransactions منتقل می‌شوند.
5. Stage لایه داخلی است؛ رابط کاربری فقط وضعیت عملیات و جزئیات خطا را نشان می‌دهد. گزارش موفق در اجرای مجدد پردازش نمی‌شود؛ گزارش ناموفق پس از رفع علت دوباره قابل اجراست.

### نکات داده‌ای
- مقادیر خالی NULL می‌مانند و صفر صریح منبع صفر ثبت می‌شود.
- واحدهای منبع تبدیل نمی‌شوند؛ ناسازگاری واحد خطا می‌دهد.
- Currency برابر IRR است؛ مقادیر مبلغ طبق مقیاس منبع حفظ می‌شوند و هیچ AmountScale اضافه‌ای اعمال نمی‌شود.
- انتقال فروش و منابع برای هر گزارش اتمیک است: اگر یک ردیف نامعتبر باشد، هیچ‌یک از ردیف‌های همان گزارش به جدول اصلی منتقل نمی‌شود.
- انتقال منابع به‌صورت Upsert انجام می‌شود و ردیف‌های موجود برای همان سند را به‌روزرسانی می‌کند؛ ردیف‌های دیگر سند حذف نمی‌شوند. مهاجرت v34 وضعیت موفق قدیمی منابع را فقط یک‌بار به PENDING برمی‌گرداند تا انتقال واقعی به جدول اصلی انجام شود.
- ستون‌های تعدیل ProductionSales از داده‌های تجمعی/اصلاحات Table_1 پر نمی‌شوند؛ فقط داده‌های بلوک «دوره یک ماهه» ثبت می‌شوند تا اصلاحات تجمعی به اشتباه به ماه جاری نسبت داده نشوند.

### آزمون
آزمون‌های واحد parser و کامپایل پایتون اجرا شده‌اند. اتصال واقعی SQL Server و اجرای مهاجرت روی دیتابیس عملیاتی از این محیط قابل انجام/تأیید نیست و باید در محیط شما انجام شود.
